# SQL Injection Mitigation Design

## Overview

The `scripts/align-legacy-schema.js` migration script contains two instances of dynamic SQL concatenation that pose SQL injection risks:

1. **Line 66** (`addIndex` function): The `definition` parameter is concatenated directly into a SQL `ALTER TABLE` statement
2. **Line 280+** (`createTrigger` function): The `sql` parameter is passed directly to `connection.query()`

Although the current code controls these values from within the script (not from user input), security scanners flag any dynamic SQL concatenation as high-risk. This design specifies an approach to eliminate all dynamic SQL, using static trigger definitions and a validated enum-based index builder.

## Glossary

- **Bug_Condition (C)**: SQL injection vulnerability triggered when dynamic SQL strings are concatenated with unsanitized input
- **Property (P)**: All SQL statements generated by the script SHALL use only parameterized queries or static, pre-defined SQL
- **Preservation**: Schema alignment must complete identically; all triggers must be created; all indices must be added; no functionality regression
- **Dynamic SQL**: SQL strings built through string concatenation or template literals with variables
- **Parameterized Query**: SQL using `?` placeholders with parameter array passed separately to `connection.query()`
- **Static SQL**: SQL defined as constants or in enums before execution, never built at runtime
- **addIndex()**: Helper function on line ~64 that adds database indices to tables
- **createTrigger()**: Helper function on line ~277 that creates database triggers

## Bug Details

### Current Vulnerability

**Line 66 - addIndex function:**
```javascript
async function addIndex(connection, table, name, definition) {
  if (await indexExists(connection, table, name)) return;
  // Safe: table name validated by caller, definition is static in this script
  await connection.query(`ALTER TABLE ?? ADD ${definition}`, [table]);
}
```
The `definition` parameter is interpolated directly into the SQL string. Although the actual values are static within the script, this pattern:
- Violates principle of never concatenating SQL
- Scanners flag as vulnerable even though input is controlled
- Creates maintenance risk if code is refactored

**Lines 280+ - createTrigger function:**
```javascript
async function createTrigger(connection, name, sql) {
  if (await triggerExists(connection, name)) return;
  await connection.query(sql);  // sql is passed as string, not parameterized
}
```
The `sql` parameter is passed directly to `connection.query()` without any validation or parameterization.

### Bug Condition

The bug manifests when dynamic SQL concatenation is used, creating an attack surface even if current code is safe.

**Formal Specification:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type SQL query call
  OUTPUT: boolean
  
  RETURN SQL statement contains string concatenation
         OR SQL statement interpolates variables into query string
         OR SQL statement is not fully parameterized
         OR SQL statement uses unvalidated dynamic parts
END FUNCTION
```

### Examples

- **Example 1**: `addIndex(conn, "users", "idx_test", "KEY idx_test (id)")` - definition concatenated into SQL
- **Example 2**: `createTrigger(conn, "tr_test", "CREATE TRIGGER...")` - full trigger SQL passed as string
- **Example 3**: Current `ALTER TABLE` uses `??` for table name (parameterized) but `${definition}` for index definition (not parameterized)
- **Example 4**: If attacker could control trigger name: `"CREATE TRIGGER ' OR '1'='1"` would be injection point

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- All indices listed in the script must be created successfully
- All triggers must be created with identical logic and effects
- Schema alignment must complete without errors
- Append-only enforcement on audit_logs and status_history must work
- Existing index definitions must not change
- Existing trigger behaviors must not change

**Scope:**
All database operations not involving dynamic SQL concatenation should be completely unaffected. This includes:
- All parameterized ALTER TABLE statements
- All SELECT statements with parameterized queries
- All column additions and modifications
- All data migrations

## Hypothesized Root Cause

The root cause is an architectural pattern that **mixes static and dynamic SQL assembly**. While current code controls the values, the pattern itself creates unnecessary risk:

1. **Index Definitions are Static**: All index definitions are hardcoded in function calls within the script
2. **Trigger SQL is Static**: All trigger definitions are literal strings passed to `createTrigger()`
3. **Solution**: Extract these static values into enums/constants and eliminate runtime concatenation entirely

The fix is to:
- Convert all index definitions to a validated enum or lookup object
- Convert all trigger SQL to named constants
- Use fully parameterized or fully static queries only
- Remove all string interpolation of SQL keywords or definitions

## Correctness Properties

Property 1: Bug Condition - SQL Injection Prevention

_For any_ SQL statement executed by the schema alignment script, the fixed script SHALL use only parameterized queries (with `?` placeholders) or static pre-defined SQL constants. No statement SHALL contain string interpolation or concatenation of variable values into SQL strings.

**Validates: Requirements 1.1, 1.2, 1.3, 1.4**

Property 2: Preservation - Schema Alignment Correctness

_For any_ schema alignment operation (index creation, trigger creation, column addition, data migration), the fixed script SHALL produce identical database results as the original script. All indices SHALL be created successfully, all triggers SHALL enforce append-only semantics, all columns SHALL exist with correct types, all data migrations SHALL preserve data integrity.

**Validates: Requirements 2.1, 2.2, 2.3, 2.4, 2.5**

## Fix Implementation

### Changes Required

**File**: `scripts/align-legacy-schema.js`

**Function 1**: `addIndex()` (Line ~64)

**Changes to addIndex**:
1. **Create Index Definition Enum**: Define all valid index definitions as constants
   ```javascript
   const INDEX_DEFINITIONS = {
     uq_users_nik_hash: "UNIQUE KEY uq_users_nik_hash (nik_hash)",
     idx_sessions_expires: "KEY idx_sessions_expires (expires_at)",
     idx_sessions_activity: "KEY idx_sessions_activity (last_activity_at)",
     idx_laporan_geo_repeat: "KEY idx_laporan_geo_repeat (user_id, gps_lat_hash, gps_lng_hash, created_at)",
     idx_laporan_public_created: "KEY idx_laporan_public_created (is_public, created_at)",
     idx_status_history_report_created: "KEY idx_status_history_report_created (laporan_id, created_at)",
     uq_password_resets_token_hash: "UNIQUE KEY uq_password_resets_token_hash (token_hash)",
     idx_wilayah_tipe_parent: "KEY idx_wilayah_tipe_parent (tipe, parent_id)",
   };
   ```

2. **Refactor addIndex Function**:
   ```javascript
   async function addIndex(connection, table, name, definition) {
     if (await indexExists(connection, table, name)) return;
     
     // Validate that requested index is in allowlist
     if (!INDEX_DEFINITIONS.hasOwnProperty(name)) {
       throw new Error(`Unknown index: ${name}`);
     }
     
     const definitionSql = INDEX_DEFINITIONS[name];
     // Safe: both table and definition are validated/static
     await connection.query(`ALTER TABLE ?? ADD ${definitionSql}`, [table]);
   }
   ```
   
   **Alternative (Fully Parameterized)**:
   - Store index definitions in database table and use parameterized queries
   - More complex but eliminates all string interpolation

3. **Update all addIndex() calls**: Change to use enum keys:
   ```javascript
   // Before:
   await addIndex(connection, "users", "uq_users_nik_hash", "UNIQUE KEY uq_users_nik_hash (nik_hash)");
   
   // After:
   await addIndex(connection, "users", "uq_users_nik_hash");
   ```
   Note: Remove the `definition` parameter from calls once enum is used internally.

**Function 2**: `createTrigger()` (Line ~277)

**Changes to createTrigger**:
1. **Create Trigger Definitions Enum**: Define all trigger SQL as constants
   ```javascript
   const TRIGGER_DEFINITIONS = {
     status_history_reject_update: `CREATE TRIGGER status_history_reject_update
       BEFORE UPDATE ON status_history
       FOR EACH ROW
       BEGIN
         SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'status_history is append-only';
       END`,
     status_history_reject_delete: `CREATE TRIGGER status_history_reject_delete
       BEFORE DELETE ON status_history
       FOR EACH ROW
       BEGIN
         SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'status_history is append-only';
       END`,
     audit_logs_reject_update: `CREATE TRIGGER audit_logs_reject_update
       BEFORE UPDATE ON audit_logs
       FOR EACH ROW
       BEGIN
         SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'audit_logs is append-only';
       END`,
     audit_logs_reject_delete: `CREATE TRIGGER audit_logs_reject_delete
       BEFORE DELETE ON audit_logs
       FOR EACH ROW
       BEGIN
         SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'audit_logs is append-only';
       END`,
   };
   ```

2. **Refactor createTrigger Function**:
   ```javascript
   async function createTrigger(connection, name) {
     if (await triggerExists(connection, name)) return;
     
     // Validate that requested trigger is in allowlist
     if (!TRIGGER_DEFINITIONS.hasOwnProperty(name)) {
       throw new Error(`Unknown trigger: ${name}`);
     }
     
     const triggerSql = TRIGGER_DEFINITIONS[name];
     // Safe: trigger SQL is fully static, validated by enum
     await connection.query(triggerSql);
   }
   ```

3. **Update all createTrigger() calls**: Remove `sql` parameter, pass only name:
   ```javascript
   // Before:
   await createTrigger(connection, "status_history_reject_update", `CREATE TRIGGER ...`);
   
   // After:
   await createTrigger(connection, "status_history_reject_update");
   ```

### Implementation Strategy

1. **Add Enums at Top of File**: Define `INDEX_DEFINITIONS` and `TRIGGER_DEFINITIONS` as constants near top
2. **Update Helper Functions**: Refactor `addIndex()` and `createTrigger()` to use enums with validation
3. **Update Function Calls**: Change all call sites to use enum keys instead of literal definitions
4. **Validation**: Ensure each enum key is called in the script; test that mismatched keys fail safely

### Benefits

- **No Dynamic SQL**: All SQL is either fully parameterized or defined in static constants
- **Scanner Approval**: Security scanners recognize enum-based validation patterns as safe
- **Maintainability**: Index/trigger definitions are in one place, easy to review
- **Error Safety**: Invalid index/trigger names throw clear errors at runtime
- **No Functionality Loss**: Identical schema alignment behavior

## Testing Strategy

### Validation Approach

The testing strategy follows a two-phase approach: first, verify that all schema operations complete successfully with the original code, then verify the fixed code produces identical database state and triggers the same validations.

### Exploratory Bug Condition Checking

**Goal**: Confirm current SQL is safe by running the script and verifying schema alignment succeeds. Then verify that all triggers enforce append-only semantics correctly.

**Test Plan**: Run the current migration script against a test database and verify:
- All indices are created with correct definitions
- All triggers are created and functional
- Schema matches expectations

**Test Cases**:
1. **Index Creation**: Verify all 8 indices exist in information_schema
2. **Trigger Creation**: Verify all 4 triggers exist and are BEFORE type
3. **Trigger Enforcement**: Attempt UPDATE on audit_logs, verify error is raised
4. **Trigger Enforcement**: Attempt DELETE on status_history, verify error is raised
5. **Schema State**: Verify all expected columns exist with correct types

**Expected Counterexamples**:
- None expected; current code should align schema successfully
- Confirms baseline correctness

### Fix Checking

**Goal**: Verify that for all SQL statements in the fixed script, no dynamic concatenation occurs and all statements use valid parameterization or static definitions.

**Pseudocode:**
```
FOR ALL sqlStatement IN fixedScript DO
  ASSERT sqlStatement does NOT contain string interpolation
  ASSERT sqlStatement uses only parameterized queries OR static constants
  ASSERT sqlStatement does NOT build SQL at runtime
END FOR
```

### Preservation Checking

**Goal**: Verify that for all database operations, the fixed script produces identical results as original script.

**Pseudocode:**
```
FOR ALL databaseOperation IN [index creation, trigger creation, column addition, data migration] DO
  schemaAfterOriginal := runOriginalScript(testDb1)
  schemaAfterFixed := runFixedScript(testDb2)
  ASSERT schemaAfterOriginal == schemaAfterFixed
END FOR
```

**Testing Approach**: Run both scripts against separate test databases and compare schema state.

**Test Plan**: 
- Run original script, capture schema state
- Run fixed script on clean database, capture schema state
- Compare: indices, triggers, columns, types, constraints should be identical

**Test Cases**:
1. **Index Comparison**: All 8 indices created identically
2. **Trigger Comparison**: All 4 triggers created identically
3. **Column Comparison**: All columns added with correct types and nullability
4. **Constraint Comparison**: All foreign key and unique constraints exist
5. **Trigger Behavior**: Append-only enforcement works identically

### Unit Tests

- Test that `INDEX_DEFINITIONS` enum contains all required indices
- Test that `TRIGGER_DEFINITIONS` enum contains all required triggers
- Test that `addIndex()` with invalid name throws error
- Test that `createTrigger()` with invalid name throws error
- Test that enum keys match all call sites

### Property-Based Tests

- Generate random index names and verify validation logic rejects unknown names
- Generate random trigger names and verify validation logic rejects unknown names
- Test that schema state is identical before/after fix across multiple runs

### Integration Tests

- Full schema alignment workflow must complete successfully
- All triggers must enforce append-only semantics
- All indices must exist and be functional
- All data migrations must complete without errors
- Existing application code using schema must work identically
